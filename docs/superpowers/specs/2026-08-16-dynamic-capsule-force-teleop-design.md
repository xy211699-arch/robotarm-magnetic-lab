# Dynamic Capsule Force Teleoperation Design

## Purpose

This task establishes the first trustworthy capsule-to-stomach rigid-body dynamics environment. It exists to answer a narrower question than capsule navigation: when a bounded force is applied to the capsule, do mass, inertia, gravity, damping, friction, collision detection, and the PhysX contact solver produce continuous and physically interpretable motion against the stomach wall?

The user explicitly requires real simulated dynamics. During normal execution, capsule translation and rotation must emerge from integrated forces, torques generated by contact, gravity, and passive material effects. The implementation must not preserve the current ideal controller's behavior of prescribing or correcting the capsule pose along the stomach surface.

## Confirmed Problem in the Current Ideal Task

`IdealSurfaceAction` explicitly enables `UsdPhysics.RigidBodyAPI.kinematicEnabled` and calls `write_root_pose_to_sim` plus `write_root_velocity_to_sim` every physics substep. The stomach collision geometry is a static triangle mesh. A kinematic capsule is not displaced by gravity, external force, or static-wall contact reaction, so direct pose writes can carry it through the stomach wall even when contacts are reported.

The current ideal task also uses 240 Hz physics with `decimation=240`, `render_interval=240`, and a 1 Hz capsule camera. Its internal trajectory has 240 samples per action, but the rendered observer sees only approximately one update per second. That sampling configuration can make a continuous internal path appear to teleport.

## Objective

Add one isolated Isaac Lab task and launcher that let a human hold six keyboard directions to apply a fixed-magnitude world-frame force to a dynamic capsule inside the existing stomach scene while viewing continuous external and capsule-camera rendering.

The task is a physics diagnostic, not a navigation controller. It must expose failures rather than hiding them with pose projection, penetration correction, surface snapping, boundary clipping, or privileged target tracking.

## Scope

The first version includes a dynamic capsule, the existing static stomach triangle-mesh collider, gravity, existing passive rigid-body damping and stomach friction, continuous six-direction world-frame force input, contact sensing, 240 Hz physics, 60 Hz environment/keyboard updates, approximately 60 Hz Kit viewport rendering, 30 Hz capsule-camera updates, runtime diagnostics, deterministic acceptance scripts, documentation, and a Linux execution report.

The first version excludes VLM integration, reinforcement learning, magnetic fields, robot or external magnet control, force-to-pose tracking, impedance control, commanded torques, deformable tissue, fluid simulation, stochastic slip, automatic surface following, automatic recovery, coverage optimization, reward design, and changes to existing task behavior.

## Non-Negotiable Real-Dynamics Contract

The capsule shall be a non-kinematic PhysX dynamic rigid body for every non-reset simulation step. Gravity shall remain enabled. The live mass and inertia shall come from the authored capsule rigid body and shall be recorded during preflight.

Direct root-pose and root-velocity writes are authorized only while resetting an episode before the next physics step. They are forbidden in the action term, keyboard loop, collision response, diagnostics, and validation recovery paths.

The applied keyboard force shall be the only active capsule actuator in this task. The task shall not include `MagneticPhysicsAction`, `LegacyMagneticCollisionBridge`, the ideal-surface action term, a hidden normal-support force, a surface constraint, or a privileged pose controller.

PhysX shall integrate capsule motion and resolve contact. A contact may redirect, reduce, or block motion. The implementation shall not interpret reduced displacement as a reason to overwrite the pose.

If the capsule penetrates, escapes through an unintended mesh opening, becomes nonfinite, or becomes unstable, the validator shall record and fail the condition. It shall not silently clamp or teleport the capsule back to a valid location.

## Dedicated Task

The Gym task ID is `Template-Robotarm-Magnetic-Dynamic-Force-Stomach-Teleop-Lab-v0`. It extends the delivered stomach scene configuration and uses exactly one environment.

The task uses `sim.dt=1/240`, `decimation=4`, and `sim.render_interval=4`. One environment step therefore represents 1/60 second while PhysX receives four substeps. The capsule camera uses `update_period=1/30` seconds. These are simulated-time cadences; actual wall-clock frame rate shall be measured rather than assumed. The Kit viewer must nevertheless render successive motion states rather than one frame per one-second action.

The task owns a three-dimensional normalized action vector in world coordinates. No robot joint action and no magnetic action is present. The action components are ordered `[Fx, Fy, Fz]` before scaling and are clamped to `[-1, 1]`.

## Force Magnitude and Composition

The default single-axis force magnitude is derived from the live capsule mass:

\[
F_0 = 0.5 m g,
\]

where `g=9.81 m/s^2`. The launcher accepts `--force_weight_ratio` so diagnostic runs can select another fixed ratio without changing source. The accepted first-version range is `0 < force_weight_ratio <= 2.0`; the default is exactly `0.5`.

A held key produces a signed unit vector. Opposite keys on the same axis cancel. If multiple orthogonal keys are held, the summed direction is normalized when its Euclidean norm exceeds one, so the total commanded magnitude never exceeds `F_0`.

The external force is applied at the capsule center of mass in the world frame at every 240 Hz physics substep. Commanded torque is identically zero. Contact forces may still generate angular acceleration because the physical contact point need not coincide with the center of mass.

## Keyboard Contract

`W` commands `+X`, `S` commands `-X`, `A` commands `+Y`, `D` commands `-Y`, `Q` commands `+Z`, and `E` commands `-Z` in world coordinates.

Force is level-triggered rather than edge-triggered. It remains active only while a key is held. Key release updates the force vector on the next 60 Hz environment step. `Space` clears every held force key, `Backspace` resets the episode, `F12` writes a diagnostic snapshot, and `Escape` exits cleanly.

The launcher shall print the current normalized direction and force in newtons whenever the held-key state changes. It shall not require an action-completion acknowledgement because force control is continuous.

## Collision and Physics Configuration

The delivered `UsdGeomCapsule` collider remains the capsule simulation shape. Preflight shall verify its radius, cylindrical height, world scale, collision enablement, non-kinematic state, gravity state, mass, inertia, and center of mass.

The delivered stomach `Physics_Collision_Mesh/Stomach` remains an exact static triangle-mesh collider. Preflight shall record its geometry hash, triangle count, boundary-edge count, collision enablement, and static status. The known 21 boundary edges shall not be relabeled as collision failures; the report must distinguish intended anatomical openings from unintended escape paths. No stomach asset edit is authorized in TASK-003.

Continuous collision detection shall be enabled both at the PhysX scene level and for the capsule rigid body using APIs verified against the installed Isaac Lab/Isaac Sim version. The preflight gate shall stop with `needs_decision` if CCD cannot be confirmed active.

The first version shall preserve delivered material friction, restitution, damping, velocity limits, and maximum depenetration velocity. It may not tune these values while implementing the force interface. Any observed instability caused by the delivered parameters must be reported before a separate tuning task is proposed.

## Components

`dynamic_force_action.py` owns action clamping, live mass-based scaling, dynamic-body and CCD gates, zero commanded torque, per-substep world-frame wrench application, wrench clearing, and diagnostic accessors.

`dynamic_force_keyboard.py` owns held-key state and maps keyboard press/release events to a normalized three-vector. It contains no Isaac Sim imports and is covered by pure tests.

`robotarm_magnetic_dynamic_force_stomach_env_cfg.py` defines the isolated task, removes every magnetic and kinematic actuator, configures the rates, and retains the existing RGB observation and contact sensor.

`teleop_dynamic_force_stomach.py` owns Kit keyboard subscription, the continuous 60 Hz `env.step` loop, reset/snapshot/exit commands, human-readable status, and external diagnostic artifacts.

`inspect_dynamic_force_prerequisites.py` verifies the live rigid body, colliders, CCD, timing, mass properties, forbidden action terms, and absence of runtime pose writers before acceptance.

`validate_dynamic_force_stomach.py` performs deterministic no-input settling and six signed force runs, records motion/contact evidence, detects nonfinite state and discontinuous displacement, and produces a machine-readable summary without correcting the capsule state.

## Runtime Data Flow

Kit press and release events update a held-key set. At each 60 Hz environment step, the keyboard adapter converts that set into a normalized three-vector. The action manager stores the vector and calls the dynamic force action term on each of the four 240 Hz physics substeps. The action term scales the vector by `0.5 m g`, writes the force at the center of mass with zero torque, and lets the standard scene write and PhysX step proceed.

After each environment step, the launcher reads observed pose, velocity, contact force, and applied wrench for display and logging only. These observations do not feed back into the actuator.

## Diagnostics and Evidence

The launcher and validator shall write outside Git under `logs/dynamic_force_teleop/<timestamp>/` or `logs/dynamic_force_validation/<timestamp>/`. Each sample shall include simulated time, root position, quaternion, linear velocity, angular velocity, normalized command, world force in newtons, commanded torque, aggregate contact force, and reset index.

The preflight JSON shall include task ID, commit, branch, physics rate, environment rate, render rate, camera rate, capsule prim path, capsule dimensions, mass, inertia, center of mass, kinematic state, gravity state, CCD state, stomach collider path, stomach geometry hash, topology statistics, contact-sensor presence, and gate result.

Screenshots, videos, JSONL traces, and generated summaries remain outside Git. The Linux report records their absolute paths, byte sizes, and SHA-256 hashes.

## Acceptance Criteria

Static configuration tests shall prove that the new task is registered separately, uses one environment, uses the frozen timing values, contains only the dynamic force action, contains no magnetic bridge, and does not instantiate the ideal-surface action.

Pure tests shall prove all six key directions, opposite-key cancellation, diagonal normalization, release-to-zero, space-to-zero, force clamping, fixed live-mass scaling, zero commanded torque, and reset clearing.

Preflight shall pass only when the capsule is dynamic, gravity is enabled, the capsule collider is a correctly dimensioned spherocylinder, the stomach collider is active and static, CCD is active, the contact sensor exists, and no forbidden actuator is installed.

The no-input settling run shall show finite state, gravity enabled, at least one stomach contact, and no direct pose write. An initially equilibrated capsule is allowed to remain nearly stationary. A small bounded solver overlap may be reported; continuous growth of penetration, nonfinite state, or an unexplained pose discontinuity fails acceptance.

The six-direction run shall prove that all six commands produce the exact signed world-frame wrench and that PhysX advances continuously for every run. Contact-constrained axes are not required to produce equal displacement. The validator shall report displacement, velocity change, maximum per-physics-step displacement, contact-force range, and minimum measured surface clearance for every direction rather than hiding constrained motion.

The rendered manual acceptance shall show continuous external-view motion and continuous 30 Hz capsule imagery while keys are held and released. Linux automation may validate startup and record a short rendered run, but the report must label subjective smoothness as unverified unless a human completes the checklist.

All existing ideal-surface, coverage, stage-one action-layer, P0 stomach, eleven-action table, and legacy table smoke tests shall be rerun to prove isolation.

## Failure and Decision Rules

Linux shall return `needs_decision` before implementation if the live capsule cannot be made non-kinematic without changing a shared asset, if the installed API cannot confirm scene-level and body-level CCD, if the capsule collision geometry differs from the delivered 25 mm by 13 mm spherocylinder, or if the stomach collision mesh used by PhysX cannot be identified unambiguously.

Linux shall return `partial` rather than tune physics if the force interface works but the delivered collision/material parameters cause sustained penetration, instability, or unintended escape. Parameter calibration is explicitly a later task because changing it in TASK-003 would prevent attribution of the observed behavior.

Linux shall never mark the task complete solely because the keyboard changes a force value. Completion requires observed dynamic motion, observed contact, continuous rendered execution, machine-readable evidence, and regression results.
